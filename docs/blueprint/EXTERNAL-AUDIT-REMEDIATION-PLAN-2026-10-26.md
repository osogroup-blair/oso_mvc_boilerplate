## Implementation rules and policy decisions

Follow `ARCHITECTURE.md`, `skills/SKILL-conventions.md`, the service/controller/route/admin/cross-cutting/private-assets/testing skills, and `docs/blueprint/{EXTENSION-CONTRACTS,DECISIONS}.md`. Services own authorization, models own SQL and transaction boundaries, controllers validate with Zod, routes apply guards, and views receive safe data. Relative imports end in `.js`. Keep soft deletion; sessions retain their documented hard-delete exception.

Use these concrete default policies for implementation and tests:

| Surface | Required policy |
|---|---|
| User directory | Authentication plus `user:read`; explicitly selected account fields only. User creation requires `user:create`; assigning a role additionally requires authority to administer roles. Never accept caller-provided hashes or arbitrary Prisma nested writes. |
| Admin boundary | All protected `/admin` routes require authentication and `admin:access`, including upload before multipart parsing and every Bull Board route. Login stays public; authenticated logout stays available to users without admin access. |
| Sensitive admin sections | Logs/diagnostics/stream: `admin:logs`; settings GET/POST: `admin:settings`; permission matrix GET: `role:read`, write: `role:update`; sessions: new `session:read` / `session:revoke`; assets: new `asset:read` / `asset:create` / `asset:delete`; queue dashboard including its APIs: new `queue:admin`. |
| Projects/tasks | Owner may operate on their own active project and its active tasks. Cross-owner administration requires current `admin:access` plus the operation's explicit `project:*` or `task:*` permission. Role name `ADMIN` alone is not an override. Task tag changes require task update authority. Project creation fixes owner to caller unless the caller has explicit administrative create authority. |
| Nested task URL | Resolve the active parent; task must have the supplied `projectId`, independently of whether the actor can access both projects. Wrong-parent task returns 404. Never authorize solely from the URL parent while mutating an unrelated task ID. |
| Organization reads | Resolve current membership before organization detail/member/options reads; list only authorized organizations. Cross-organization access requires a new explicit `organization:admin` permission, not a global role name or `admin:access` alone. |
| Organization writes | OWNER/ADMIN can update metadata and manage ordinary members in their active organization; OWNER alone can grant/revoke OWNER or ADMIN and delete the organization. ADMIN cannot alter an OWNER/ADMIN membership or promote themselves. `organization:create` permits creation; `organization:admin` is the explicit platform override. All paths, including override, preserve at least one owner. Admin web pages additionally require the admin boundary. |
| Organization user chooser | Showing the full active user directory also requires `user:read`. Authorized org managers without that permission may add a known user ID under member-management policy, but receive no global user list. Do not expose email search as an alternative directory bypass. |
| Public project reads | Preserve the existing demo's intentional public read behavior; these tables have no organization foreign key. Do not invent tenant ownership or a schema migration to organization-scope them as part of F2. Document this limitation for generated applications. |

Missing actor, deleted/inactive actor or parent, revoked membership, and missing permission must fail closed. Pass actor identity explicitly into service commands; resolve current role/membership from trusted storage. Do not treat form fields, cached UI permissions, hidden buttons or a membership in a different organization as evidence of access. Use 401 for unauthenticated API requests, 403 for known unauthorized operations, and 404 for parent-child mismatch or absent resources. Preserve browser login redirects where appropriate.
